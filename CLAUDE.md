## What this project is

A stateless PDF generation microservice. It receives a workflow graph (JSON) or a direct template definition plus a data payload, then returns a rendered PDF as binary bytes. No database, no caching, no persistence — every request is independent.

## Commands

```bash
# Start the API server
python run.py server --host 0.0.0.0 --port 8080 --reload

# Directly render a template file to PDF (CLI, no server needed)
python run.py render --template workflow.json --data data.json --out doc.pdf

# Smoke test: generate a minimal PDF without any files
python run.py test-render

# Run all tests
pytest tests/

# Run a single test file
pytest tests/test_integration.py

# Run a single test by name
pytest tests/test_integration.py::test_render_minimal_template
```

Swagger UI is available at `http://localhost:8080/docs` while the server is running (auto-generated by FastAPI).

## Core pipeline: three stages

The entire rendering flow is a linear pipeline. Understanding the handoff between these three stages is essential:

```
POST /generate or /render
        │
        ▼
1. workflow/executor.py          ← Only for /generate (workflow JSON with nodes/edges)
   Topological sort (Kahn's), executes nodes in order:
   webhook-trigger → data-processor → document-designer
   Produces: templateJson + resolved data dict
        │
        ▼
2. pdf_engine/normalize.py       ← Always runs
   Strips UI-only fields (createdAt, zIndex, locked, pagePreview)
   Builds lookup indexes: contentAreas by id, assets by id
   Collapses border/fill shorthand into structured objects
        │
        ▼
3. pdf_engine/page_renderer.py   ← Always runs
   Creates ReportLab canvas, iterates pages and elements
   Dispatches each element to its renderer in pdf_engine/renderers/
   Returns raw PDF bytes
```

## Coordinate system (critical detail)

The JSON schema uses **millimetres** with **Y increasing downward** (CSS convention). ReportLab uses **points** with **Y increasing upward** (PDF convention). All conversion happens in [pdf_engine/coordinate.py](pdf_engine/coordinate.py):

- `1 mm = 2.8346 pt`
- `pdf_y = page_height_pt − json_y_mm_to_pt − element_height_pt`

Every renderer must go through the helpers in `coordinate.py` — never do raw arithmetic to convert positions.

## Renderers

Each element type in `pages[].elements[].type` maps to a file in `pdf_engine/renderers/`:

| type | renderer file |
|---|---|
| `contentarea` | contentarea_renderer.py |
| `table` | table_renderer.py |
| `image` | image_renderer.py |
| `text` | text_renderer.py |
| `shape` | shape_renderer.py |
| `qr` | qr_renderer.py |
| `barcode` | barcode_renderer.py |

`page_renderer.py` is the dispatch hub — it reads the element type and calls the right renderer. All renderers receive the same signature: `(canvas, element, data, assets, styles, fonts, page_height_pt)`.

## ContentArea rendering (most complex path)

`contentarea` elements contain rich HTML markup. The rendering chain is:

```
HTML string
    ↓ html_parser.py      → parses tags, resolves <span class="var-tag">, builds TextRun list
    ↓ area_resolver.py    → evaluates inline conditions (trueAreaId / falseAreaId branching)
    ↓ variable_resolver.py → substitutes ${var} and dot-notation paths (e.g. user.address.city)
    ↓ contentarea_renderer.py → feeds TextRuns into ReportLab Paragraph/Platypus
```

Special variables available in any content area: `$pageNumber`, `$pageCount`, `$today`, `$now`.

Conditional areas use `flowType: "inline-condition"` and branch to `trueAreaId` or `falseAreaId` evaluated via `selectionScript` or `selectionVariable`.

## Style resolution

Styles are declared centrally in `templateJson.styles` (TextStyle, ParagraphStyle, BorderStyle, FillStyle). Elements reference them by id. `pdf_engine/style_registry.py` handles lookup, fallback merging, and conversion to ReportLab equivalents.

Inline `border` and `fill` objects on elements override the style registry values.

## Font resolution order

`pdf_engine/font_manager.py` resolves fonts in this priority:

1. Explicitly declared in `templateJson.fonts[]` (path on disk)
2. Bundled fonts in the `fonts/` directory
3. Auto-detected system fonts (scanned at startup)
4. ReportLab built-ins: Helvetica, Times-Roman, Courier

If you add a new font family, drop the `.ttf`/`.otf` files into `fonts/` — the manager detects bold/italic variants by filename keywords (`bold`, `italic`, `oblique`).

## Workflow node types

The `workflow/executor.py` supports these node types executed via topological sort:

- **webhook-trigger** — defines the schema and injects default values into the data context
- **data-processor** — field mappings with optional transforms (`uppercase`, `lowercase`, `capitalize`, `trim`); writes results back into the data dict
- **document-designer** — holds the `templateJson`; this node's config becomes the template
- **data-viewer** — read-only inspection node, no side effects

## API endpoints

| Method | Path | Body | Returns |
|---|---|---|---|
| `POST` | `/generate` | `{ "workflow": {...nodes/edges...}, "data": {...} }` | PDF bytes |
| `POST` | `/render` | `{ "templateJson": {...}, "data": {...} }` | PDF bytes |
| `GET` | `/health` | — | `{ "status": "ok" }` |
| `GET` | `/test-render` | — | PDF bytes (smoke test) |

`/generate` also accepts the workflow unwrapped at root (without the `"workflow"` key) for compatibility with older callers.

## Test fixtures

`tests/conftest.py` defines three shared fixtures used across most tests:

- `minimal_template` — Single A4 page with one contentarea + one shape
- `minimal_data` — `{"name": "Oscar", "userId": 42, "plan": "pro"}`
- `workflow_with_webhook` — Full graph: webhook-trigger → data-processor → document-designer

Integration tests validate output as valid PDF by checking `output[:4] == b"%PDF"` and file size thresholds.
